# Persistent runtime memory

C07 introduces `context_engine.memory.MemoryStore` in package 0.7.0. It stores application conversations, not the development Markdown brain. No inference, credentials, global database location or customer ingestion is implicit. Run `uv run --locked context-engine memory-demo` for a synthetic, temporary-store walkthrough.

## SDK boundary

```python
from datetime import UTC, datetime
from context_engine.config import BudgetConfig
from context_engine.memory import MemoryStore
from context_engine.models import Message, Role, Scope, Turn

memory = MemoryStore("/private/tmp/my-context-example/memory.sqlite")
scope = Scope("authorized-tenant", "session-1")
revision = memory.create_scope(scope)
turn = Turn("t1", scope, (Message("m1", Role.USER, "Database: PostgreSQL"),),
            timestamp=datetime.now(UTC))
memory.put_turn(turn, operation_id="ingest-1", expected_revision=revision)
snapshot, context = memory.assemble(
    scope, "Which database?", BudgetConfig(input_cap=900), system="Use the supplied evidence."
)
metadata = snapshot.to_dict()  # Content export requires include_content=True.
```

This is a trusted in-process SDK, **not authentication**. Authorize tenant/session access before calling it; C08 supplies the service boundary. Store-wide backup, restore and `prune()` are privileged maintenance operations, not tenant endpoints. Use private application-owned paths outside the project brain. IDs can themselves be sensitive: use opaque identifiers and do not log private snapshots.

`put_turn` requires a complete validated turn, including paired tool calls/results. Turn/pin revisions start at 1 and advance exactly once. `expected_revision` is the **scope** revision, not the individual record revision. Mutations use optimistic compare-and-swap within transactions; source-pin invalidation may advance scope revision more than once. Read a fresh snapshot before the next independent mutation. Repeated ingestion with an identical operation ID, payload and expiry returns the original receipt without duplication. Reusing that ID for different input conflicts. An old receipt never recreates a subsequently deleted turn.

Snapshots contain immutable originals, active pins and an optional caller-supplied summary. Identity binds epoch, scope revision and content; future pin activation changes identity even without a write. `assert_current` rejects stale snapshots. Summaries must match exact history, revisions and expiry; mutations invalidate summary/replay. No summaries are generated by C07. External generators own model/config/cost records and supply a versioned summary policy.

## Indexing and inference

`index_batch(snapshot, batch_size=32)` processes at most 256 turns per transaction and reports `BUILDING`/`READY`, processed and remaining counts. Reopen and call again with the current snapshot to resume. `chunk_index` refuses incomplete/corrupt coverage. Edits re-chunk only changed originals; a configuration change replaces the scope's active profile. Source hashes, chunk-set digests and source references are checked before reuse. Stale work conflicts rather than mixing revisions.

Persisted **chunks and coverage** are reused. BM25 still builds for each request's eligible old-history subset, preserving WINDOW exclusion and existing scoring. This is not persistent BM25 postings, a measured performance claim or an S11 quality fix. `assemble` finishes bounded batches synchronously; use `index_batch` for application-managed progress/cancellation between transactions.

Optional `context_engine.providers.memory.MemoryProvider(memory, client, replay=False)` binds inference to the actual snapshot. Replay is opt-in; the C05 client's own body cache must be disabled. Memory owns replay expiry/deletion; hits validate original accounting receipts and record zero new provider spend. A revision change during inference discards the answer while retaining charged usage. An already sent request cannot be recalled from a provider, and externally exported snapshots cannot be revoked. Use this bridge or equivalent revision checks; manually exported requests fall outside managed lifecycle guarantees.

## Retention and deletion

Turns accept `expires_at`; pins/summaries use contract expiry. Successful operations apply cleanup before returning data. `prune()` commits maintenance independently; there is no background timer. Failed transactions roll back cleanup too, so applications should schedule successful maintenance to physically purge rows.

`delete(scope, kind="turn" | "pin" | "scope", key=..., expected_revision=...)` tombstones the identifier permanently; deleted IDs cannot be reused. Turn deletion/revision removes its chunks/coverage, tombstones pins citing it, and invalidates scope summaries/replay. Unknown-target deletion also tombstones. Whole-scope deletion removes live contents and ingestion receipts. The deletion ledger retains identifiers, not prompt/answer bodies; receipts retain hashes. Unsourced pins cannot be inferred to derive from a turn: provide provenance or delete them explicitly.

Per-scope bounds: 10,000 turns/8 MB encoded originals; 1 MB per turn; 256 pins/64 KiB each; 256 KB summary; 100,000 chunks; 100 replay entries/1 MB each, TTL at most one day. Tombstones and ingestion receipts accumulate as correctness records. Total database/tenant quotas, compaction and load qualification remain C08–C10 work.

## Backup and deletion-safe restore

The main SQLite file stores live state; a second file (default `memory.deletions.sqlite`) is the deletion authority. Attached-database transactions use rollback journals and FULL synchronization; WAL is rejected, following SQLite's [cross-file atomicity requirements](https://www.sqlite.org/lang_attach.html).

`backup(new_path)` uses the [SQLite backup API](https://www.sqlite.org/backup.html), refuses overwrite and copies the main database **only**. Retain the deletion authority separately and capture `deletion_watermark()` in trusted recovery metadata:

```python
restored = MemoryStore.restore(
    backup_path, new_database_path,
    deletion_path=current_authoritative_deletion_ledger,
    minimum_deletion_seq=trusted_latest_watermark,
)
```

Restore checks lineage, contiguous deletion sequence and minimum watermark before copying, then applies current tombstones before exposing data. It rotates the epoch, invalidates old snapshots and clears chunks, summaries and replay for rebuilding. Missing/wrong/stale authority fails closed. **Never roll back the deletion ledger with the backup.** If both files and the external watermark are rolled back, this local implementation cannot detect lost newer deletions. Protect authority and watermark independently; disaster-recovery objectives and authority replication remain C10.

Backups/exports still physically contain their historical data and need operator retention policies. Current tables use `secure_delete=ON`, not certified filesystem, SSD, provider or cryptographic erasure; see [SQLite limitations](https://www.sqlite.org/pragma.html#pragma_secure_delete). Failed copying may leave a private incomplete destination: quarantine it, do not serve it. Recovery refuses to overwrite that path.

## Schema and deployment path

Both files use schema version 1. Unsupported versions fail without migration; never relabel `user_version` to bypass checks. C00–C06 had no conversation database to migrate, and provider accounting remains separate. Tests cover creation/reopen, unsupported-schema refusal, corruption and rollback. A future SQLite/PostgreSQL migration must preserve lineage, revisions, ingestion receipts and current tombstones; reapply deletions before traffic, rebuild derived data and pass the lifecycle tests. Copying only history is insufficient. PostgreSQL migration code and production crash/load qualification are not delivered here.

Files are private regular files (0600 on POSIX), with no-follow opens and strict JSON rather than object deserialization. Parent directories/local administrators are trusted. Hashes detect accidental corruption, not wholesale malicious rewriting. Windows ACLs, encryption, hostile-filesystem races, distributed concurrency and production recovery remain later enterprise gates.
